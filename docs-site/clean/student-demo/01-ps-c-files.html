Instructor preparation notes for the student Lorenz demo: keep the board support and reusable drawing tools; let students write the solver interface, controls, and plots.

Status: preparation plan, not a completed student release. Proposed helper APIs and tests below still need implementation and validation. The C files have not been changed by this documentation update.

Students may put their application code in video_demo.c. The drawing portion of lorenz_dda can become a small supplied drawing.c/.h library. Keep a complete instructor solution separately, and remove instructor-only notes from the final handout.

Drawing helpers: proposed supplied interface

Your notes call for point, line, filled/unfilled rectangle, and text primitives. The library should handle framebuffer writes; students should build the Lorenz plots from those primitives. The following names describe a proposed API, not functions already available.

Proposed callContract to settle before implementation
plot_point(x, y, color)Absolute screen pixels, origin at top left. Decide whether a point is 1x1 or has configurable size; compare visibility with the current 2x2 dot.
draw_line(x0, y0, x1, y1, color)All directions, including a single-point line; clip to the active drawing surface.
draw_rect(x, y, width, height, color)
fill_rect(x, y, width, height, color)		Outline and filled rectangles, predictable edge inclusion, zero-size handling, and clipping. A full-screen black fill provides a simple reset.
draw_text(x, y, text, color)Document glyph coverage, text size, pixel coordinates, and background behavior. Support useful labels rather than only X/Y/Z/S/R/B/D.
Optional draw_float(...) and clear_screen(color)Convenience wrappers. Numeric redraw must erase the previous field so shorter values do not leave old digits.

Framebuffer ownership: choose either an explicitly passed drawing context or one initialized context that stores the current frame pointer, stride in bytes, width, and height. The short calls above assume that context has already been bound. Avoid hard-coding 1920x1080 inside each primitive.

Color contract: the current code stores bytes in Red, Blue, Green order at x * 3 + y * stride. A public RGB color type can be easier to use, but the helper must translate it to the actual framebuffer order. Confirm with red/green/blue patches on HDMI.

Bounds and text: existing rectangle/glyph/line routines assume valid coordinates. Add a documented clip-or-reject policy before exposing them to arbitrary student input; handle negative coordinates before conversion to unsigned offsets. DrawLabel does not erase its background; the float helper clears a fixed 12-character region. Unsupported glyphs currently draw nothing. These behaviors need explicit decisions and tests.

Keep solver work outside the helper: the supplied library should not step the IP, read registers, choose phase-plane ranges, or silently batch 16 solver steps. Students own the XY/YZ/XZ projection and redraw policy. Drawing into DDR also needs cache visibility for VDMA: preserve a caller-side flush example, or provide a documented present/flush helper after a batch of drawing.

Next changes, in order

  1. Freeze the handout boundary. Preserve a working instructor solution; decide which register-map hints, function signatures, UART examples, and display-mode interface are supplied.
  2. Extract and validate the drawing library first. Move reusable primitives and font data into drawing.c/.h, expose the public functions, and remove dependencies on solver registers and fixed panel geometry. The current text and line helpers are static, so they cannot simply be called from another C file.
  3. Build a minimal helper demonstration. Bring up HDMI, clear the screen, draw colored points/lines/rectangles and text, read one UART value, redraw it, and flush the framebuffer. Prove this without the Lorenz IP before stripping the full application.
  4. Create the student skeleton. Replace completed solver, menu, projection, and layout code with clear TODOs. Update headers and build sources together; compile only the intended application/helper files, avoiding duplicate definitions from solution/template copies.
  5. Resolve source inconsistencies. The parameter comment describes rho=28 and beta=8/3, while the template initializes rho=25 and beta=2. The speed-up comment says a 100 us floor, while its condition allows the delay down to 1 us; doubling can exceed the stated 1 s cap. Choose intended behavior and make comments and code agree.
  6. Run the checks below, then prepare the handout. Remove INSTRUCTOR NOTE comments from student files, retain student-facing API guidance, and record tested display modes and known limitations.
